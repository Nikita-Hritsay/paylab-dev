# Payment Provider

A small Spring Boot microservice that wraps the [LiqPay](https://www.liqpay.ua/) payment gateway behind a simple REST API. Other services (for example `orders-api`) call this service instead of talking to LiqPay directly, so LiqPay credentials, request signing and API quirks live in one place.

## What it does

- Creates **invoices** that LiqPay emails to a customer.
- Builds **checkout** payloads/forms so a frontend can redirect a customer to the LiqPay payment page.
- **Verifies webhook signatures** so callers can trust that a payment notification really came from LiqPay.
- Looks up the **status of a payment** by order id.

The service is stateless. It has no database and stores no payment data. Every call is translated into a LiqPay request (or a local signature computation) and the result is returned.

## Tech stack

- Java 17
- Spring Boot 4.1.2 (`spring-boot-starter-webmvc`)
- LiqPay Java SDK (`liqpay-sdk` 0.8-SNAPSHOT)
- Lombok
- Maven (wrapper included)

## How it works

```
 Client / orders-api ──► LiqPayProviderController ──► LiqPayProviderService ──► LiqPay API
                              (REST, /api/v1/...)        (build params, sign)      (https://www.liqpay.ua)
```

| Layer | Class | Responsibility |
|-------|-------|----------------|
| Controller | `LiqPayProviderController` | Exposes the REST endpoints and maps request bodies to DTOs. |
| Service | `LiqPayProviderService` | Builds LiqPay parameters, calls the SDK, signs data, verifies signatures. |
| Config | `LiqPayConfig` | Creates the `LiqPay` SDK bean from `public_key` / `private_key`. |
| DTOs | `CreateInvoiceDTO`, `CreateCheckoutDTO`, `VerifyWebhookDTO` | Request payloads. |
| Exceptions | `LiqPayException` | Thrown when LiqPay rejects or fails a request; mapped to HTTP `502 Bad Gateway`. |

### LiqPay request model

Every LiqPay call carries an `action` (`invoice_send`, `pay`, `status`) and `version` (`3`) plus action-specific fields. For browser-based flows LiqPay expects two values:

- `data`: the parameters as JSON, Base64-encoded
- `signature`: `Base64(SHA1(private_key + data + private_key))`

The service produces and checks these itself.

### Typical payment flow

1. A client asks this service to create an invoice or checkout for an order.
2. The customer pays on the LiqPay page (or from the emailed invoice link).
3. LiqPay sends a webhook (`data` + `signature`) to the caller's server.
4. The caller forwards `data` and `signature` to `/verifyWebhook` to confirm authenticity.
5. At any time the caller can check `/paymentStatus` for an order.

## API

Base path: `/api/v1/liqPayProvider`

### `POST /createInvoice`

Sends a LiqPay invoice to the customer's email. Calls LiqPay's `invoice_send` action and returns LiqPay's response as JSON.

```json
{
  "email": "customer@example.com",
  "amount": "100.00",
  "currency": "UAH",
  "orderId": "1001",
  "goods": [
    { "amount": "100.00", "count": "1", "unit": "pcs", "name": "T-shirt" }
  ]
}
```

- If LiqPay returns `result: "error"`, the service responds with `502` and the LiqPay error description.

### `POST /createCheckoutForm`

Returns a ready-to-embed **HTML form** (string) generated by the LiqPay SDK. Submitting it sends the customer to the LiqPay checkout page.

```json
{
  "amount": "100.00",
  "currency": "UAH",
  "description": "Order #1001",
  "order_id": "1001"
}
```

### `POST /createCheckout`

Same request body as `/createCheckoutForm`, but returns the raw signed payload so a frontend can build its own form or use the LiqPay checkout widget.

```json
{
  "data": "<base64 payload>",
  "signature": "<base64 signature>"
}
```

### `GET /verifyWebhook`

Checks that a webhook really came from LiqPay by recomputing the signature over `data` and comparing it (constant-time) with the supplied `signature`. Returns `true` or `false` (`false` if either field is missing).

```json
{
  "data": "<data from LiqPay webhook>",
  "signature": "<signature from LiqPay webhook>"
}
```

> Note: this endpoint is a `GET` that reads a JSON request body. Some HTTP clients and proxies drop bodies on `GET` requests.

### `GET /paymentStatus?orderId={id}`

Queries LiqPay's `status` action for the given order and returns the LiqPay response as JSON (e.g. `status`, `amount`, `payment_id`).

## Error handling

| Situation | Result |
|-----------|--------|
| LiqPay rejects an invoice (`result: "error"`) | `LiqPayException` → HTTP `502` with the LiqPay message |
| Network/SDK failure calling LiqPay | `LiqPayException("LiqPay request failed")` → HTTP `502` |
| Webhook signature mismatch or missing fields | `verifyWebhook` returns `false` |

## Configuration

Set in `src/main/resources/application.properties` (or a local override such as `application.local.properties`):

| Property | Description |
|----------|-------------|
| `public_key` | LiqPay public key |
| `private_key` | LiqPay private key. Keep it secret. |

Do not commit real keys. Prefer environment variables (`PUBLIC_KEY`, `PRIVATE_KEY`) or an untracked local properties file.

## Running

```bash
./mvnw spring-boot:run     # start the service (default port 8080)
./mvnw test                # run tests
./mvnw clean package       # build the jar in target/
```

## Notes and current limitations

- Checkout requests are hard-coded to LiqPay **sandbox mode** (`sandbox=1`) in `LiqPayProviderService.createCheckoutParams`. Remove or make it configurable before going to production.
- `paymentStatus` takes `orderId` as an `Integer`, while the other endpoints use strings.
- There is no authentication on the endpoints; the service is intended to run behind an internal network or gateway.
- No payment state is persisted here. Callers are responsible for tracking orders.
